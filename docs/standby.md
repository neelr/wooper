# Papery standby

On Duo (iPhone19,4 / iOS 27.1), the main Papery tab enters standby after 3 seconds idle with `DeviceHinge.Status.partiallyOpen`. Opening flat or closing exits immediately. Opening a bookmark suppresses automatic re-entry until the next hinge-status change. There is no back button; unfolding or closing exits. DS, comics, keyboard entry, presented sheets, background scenes, and held touches cannot trigger entry. A passive window gesture recognizer resets the idle deadline without taking over list gestures. SwiftUI's `onHingeChange` observes the persistent root content, outside both the Papery hit-testing modifier and the standby overlay. It receives live hinge updates without a manually attached UIKit interaction or hinge polling; unchanged partial-open readings do not restart the idle deadline. This follows [Apple's Duo hinge example](https://developer.apple.com/videos/play/tech-talks/111464/). Debug builds save local trigger diagnostics to `Documents/standby-debug.json` for physical fold verification.

The physical hinge axis, converted from the screen's fixed coordinate space, chooses side-by-side book panels or stacked tabletop panels. The cream canvas uses larger, medium-weight Papery monospace typography and darker text. Entry uses a single opacity dissolve over the stationary Papery screen, with no blur or slide. Status-bar changes wait until the dissolve finishes; the standby canvas ignores safe-area changes. Reduce Motion shortens the dissolve. Weather, bike, and playback data are retained across entries to avoid repeated empty loading layouts. The clock/date and battery stay in place; unread bookmarks shuffle without replacement every 30 seconds, pausing during interaction. Tapping a bookmark returns to Papery and opens its URL. Bookmarks appear as large, top-aligned page previews with a two-line title and smaller domain beneath the image. In book posture the preview fills the companion half’s width, without a heading above it. From 22:00 to 06:00, brightness is capped at 15% while active; prior brightness, battery monitoring, and idle-timer settings are restored on exit. The display stays awake only while standby is active.

Location is requested on first entry, used only while standby is active, and stopped in inactive scenes. Without access, weather/map use a clearly labeled central-SF fallback; no user dot or walking estimate is shown. Bike distances use a straight-line estimate with a 1.3 route allowance and 80 m/min walking pace; the UI labels time approximate. Pins select a bike/station, and the detail opens the feed's official Lyft rental URL (not a booking).

Data providers:
- Weather: https://open-meteo.com/en/docs — local conditions, highs/lows, wind, sunrise/sunset, and approximate 15-minute precipitation timing; refreshed every 15 minutes (retry every minute on error).
- Tides: https://api.tidesandcurrents.noaa.gov/api/prod/ — station 9414290 (San Francisco/Golden Gate), high/low predictions, feet relative to MLLW; GMT timestamps parsed explicitly. This is not an Ocean Beach-specific prediction. Shows the next future low, labeling tomorrow when applicable.
- Bikes: https://gbfs.lyft.com/gbfs/1.1/bay/gbfs.json — station information, station status, and free-bike status. Availability refreshed every minute; disabled/reserved bikes and non-renting stations excluded. The initial map frames nearby available bikes within 5 km. Pins then follow the visible map as you pan, with up to 120 markers; empty stations remain visible with zero counts. All bikes are shown by default, with an e-bike filter and recenter control. Counts older than five minutes are visibly stale. MapKit provides the native map and its attribution.

All polling tasks cancel with the standby view or inactive scene. No camera session is needed. No background location permission, new credentials, or provider API keys are used.

The forecast test optionally accepts a directory with captured `standby-weather.json`, `bay-station_status.json`, `bay-station_information.json`, and `bay-free_bike_status.json` provider responses to check live schemas. The full app is built with the usual Wooper device scheme; real hinge behavior requires Duo hardware.

Spotify: the phone cannot read the local Spotify app's playback state without an authorized Spotify App Remote session. Standby instead uses the user's `https://neelr.dev/api/spotify` fallback, polling every 15 seconds only while active. A compact track/artist/device row with a slowly rotating vinyl record appears below the date only for playing responses and expires after 45 seconds without a successful response. Paused, empty, or failed responses hide it. Reduce Motion disables the spin; inactive scenes pause it. Tide and sunrise/sunset details use smaller 13-point text. Tapping opens the track; the app does not change playback. No Mac scripting is used by Flippy.

The one-second clock/bookmark task is tied to the standby view identity, not a Timer publisher re-created by parent updates. This prevents the main screen's idle ticks from continually restarting the bookmark countdown.

The bike map starts with an explicit camera region. Since its markers are selected from the viewport, an automatic camera would feed marker changes back into camera changes. Each render selects and ranks markers once and shares the selected ID with annotation closures. Distances are calculated once per candidate before sorting, rather than allocating Core Location objects in every sort comparison. This avoids the main-thread stall observed when re-entering standby with a populated bike feed. The forecast checks include nearest-first selection and the 120-marker cap against a 5,000-station feed.

The outer display also supports tent standby while Papery is open in landscape (compact horizontal and vertical size classes). The phone reports the hinge status as `closed` even while tented at roughly 38°, so this layout uses the actual angle: entry at 15°–150°, retaining the pose within 10°–160° to avoid threshold flicker. The same three-second idle/touch/sheet gate applies. Fully closed, flat, and portrait phone use do not enter tent standby. No camera session or accessory scene is needed; this uses the main app on the active outer display, following [Apple's landscape/tent guidance](https://developer.apple.com/videos/play/tech-talks/111461/).

The compact layout lowers the clock/date/music and groups weather, the nearest Lyft bike, and tide/sun times into a vertically centered stack with consistent gaps. The source/battery footer stays at the bottom. The compact bike row shows availability, approximate walk time, and the station name; tapping it opens the feed's Lyft rental URL. Stale availability is labeled. The right side is a full-height rotating bookmark preview; the small screen has no map or page controls. Bookmark timing and provider data are shared with the expanded layout. Content respects the active window's asymmetric safe-area insets, and night dimming/restoration targets that window's display rather than `UIScreen.main`.

Both layouts show a rain line only when rain is approaching or ongoing, using relative wording such as `rain in ~10 min` or `rain easing in ~20 min`. Dry, missing, or stale forecasts leave the line hidden. Open-Meteo's precipitation bins cover the 15 minutes ending at each timestamp, so countdowns use interval starts and are rounded to approximate five-minute increments. Forecast gaps/nulls are not treated as dry weather. The model forecast is approximate, not a minute-resolution radar nowcast.

Both standby layouts place the user's transparent [hippo artwork](https://neelr.dev/hippo.png) to the right of the low-tide details. The original image is bundled in `StandbyHippo.imageset`, so it does not depend on a network request. It is decorative and excluded from hit testing and VoiceOver.
